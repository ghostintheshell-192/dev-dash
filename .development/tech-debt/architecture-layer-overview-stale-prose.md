# ARCHITECTURE.md "Layer Overview" table is hand-written prose frozen at the ADR-010 pivot, not derived from source

## Problem

The "Layer Overview" table at the top of `ARCHITECTURE.md` — auto-imported into
every Claude Code session via `.claude/CLAUDE.md` — describes
`app/src/services/` as: *"DocumentLoader (fully implemented); stubs for
ConfigResolver, DiffEngine, ApplyEngine, SnapshotService, ScaffoldRepository."*

This is false as of today. All five "stub" services are fully implemented,
wired, and have been in `develop` since 2026-05-12/14 (see
`CURRENT-STATUS.md`, entries `2026-05-12` and `2026-05-14`):

- `ConfigResolver` — orchestrates seven adapters (claude_md, rules, memory,
  skills, agents, mcp, hooks) into an `EffectiveConfig`
- `DiffEngine` — full tree comparison (kMissing/kModified/kUnchanged/kCustom),
  optional content capture
- `ApplyEngine` — file apply with pre-apply autosnapshot integration,
  per-file skip/fail accounting
- `SnapshotService` — save explicit/auto, list, restore, automatic pruning,
  metadata parsing — the most substantial module in `services/`
- `ScaffoldRepository` — lazy-cached listing, case-insensitive sort, default
  marking, create/copy/delete

Since the table sits directly above the auto-generated "Project Tree" section,
and both carry the file's blanket footer *"Auto-generated by
generate-architecture.sh"*, there is no visual or structural signal
distinguishing verified-fresh content from six-week-old hand-written prose.
Every new session inherits this misinformation about the project's most
distinctive feature (the effective-configuration resolver) at zero cost and
with full apparent authority.

## Analysis

Root cause: `generate_project_header()` in `generate-architecture.sh` prints a
**hardcoded heredoc** (`cat << 'EOF' ... EOF`), not anything derived from
`app/src/services/*.cpp`. It was accurate when written — around the ADR-010
split, 2026-05-10, when only `DocumentLoader` existed. The script has run on
every commit since (correctly regenerating the Project Tree below), but
nobody has had a reason to open the *script itself* and edit its embedded
prose, because the file's footer gives no indication that part of it isn't
actually regenerated.

This is the same category of failure as
`scaffold-architecture-eval-glob-expansion.md`, in the same script, with the
opposite symptom: that bug can make the tree **silently empty**; this one
makes a *section* **silently wrong** while everything around it looks equally
fresh.

## Possible Solutions

- **Option A — derive stub/implemented status from source (recommended)**:
  have `generate_project_header()` (or a helper) check each named class's
  `.cpp` file — e.g. line count above a threshold, or absence of a
  `// STUB` marker comment — and generate the Services row's prose
  programmatically instead of hardcoding it. Closes the drift permanently;
  requires deciding a convention for marking genuine stubs (e.g., a
  `// TODO: stub` comment) so short-but-complete files aren't misclassified.
- **Option B — timestamp the hand-written section**: add a
  `<!-- layer-overview last reviewed: YYYY-MM-DD -->` comment immediately
  above the Layer Overview table, updated manually whenever it's checked
  against source. Doesn't fix the content, but makes the staleness visible
  instead of invisible — a model or a human glancing at the file can see it
  hasn't been reviewed since May.
- **Option C — drop the Services row's implementation-status claims
  entirely**: keep the table to structural facts only (path, one-line
  purpose), and point to `CURRENT-STATUS.md` for what's implemented vs.
  planned. Removes the failure mode by removing the claim, at the cost of a
  slightly less informative table.

## Recommended Approach

**Option A** for `services/` specifically (it's the layer that actually
changes implementation status over time); **Option B** as a cheap safety net
for the rest of the header prose, which is more structural and less likely to
drift but not immune to it.
